# P10 · 跨会话偏好与会话历史

2026-11-26 · 已批准 · 实施基线 `p9-faq-hybrid-retrieval` 的 `af4308a`

## 目标与已确认决定

登录用户在聊天中明确说“请记住”并提供可识别的住宿偏好时，服务端直接保存并在聊天中回复保存结果，无需二次确认。本人的下一次酒店查询可使用最新偏好，当前请求的明确条件优先。用户可查看、修改和删除保存值。删除提交后，后续请求读取不到该值，即使旧聊天、旧检查点和早期原文还保留这次保存的记录。

本阶段同时支持在同一会话中引用早期酒店查询，例如用户在数轮无关对话后说“按上次的酒店条件再查”。系统找回本人之前明确给出的入住条件，并重新核验航班和库存。原始消息继续按会话归属保存。

用户已选择 PostgreSQL 业务表。它复用现有认证、Alembic 迁移和事务机制，支持按字段更新和删除，并供 `/api/me` 直接读取。LangGraph Store 也支持跨会话命名空间，但需要接入另一套存储生命周期和业务字段约束。父图继续使用现有 LangGraph PostgreSQL 检查点处理会话恢复。

## 偏好字段和管理接口

首版建议支持三个可空字段，与现有苏黎世合成库存对应。

| 字段 | 取值与含义 |
| --- | --- |
| `room_type` | `standard`，对应标准房 |
| `area` | `airport` 或 `city`，对应机场附近或市区 |
| `max_total_chf_minor` | 从 1 到 1,000,000 的整数，以瑞郎分表示整段住宿总价上限，含等于上限 |

- `GET /api/me/preferences` 返回三个字段，无保存值时为 `null`。
- `PATCH /api/me/preferences` 接受至少一个受支持的字段。省略的字段保留，显式 `null` 清除相应字段。返回更新后的三个字段。未知字段、空对象、类型或取值错误返回 `422`，整次更新无副作用。
- `DELETE /api/me/preferences` 清空当前账号全部偏好，重复调用返回 `204`。之后 `GET` 返回三个 `null`。
- 三个接口复用登录 Cookie，服务端从认证得到用户 ID。请求体无账号字段，未登录请求返回 `401`。备选房型和其他币种留待实际库存引入时扩展。

存储增加 Alembic 迁移和一张以用户 ID 为主键的业务表。写入使用原子字段级更新和数据库约束。并发修改不同字段时保留两次修改，修改同一字段时以数据库写入顺序为准。删除与后续显式保存按数据库写入顺序生效。发生数据库错误时返回现有服务错误结构，聊天不显示保存成功。应用就绪检查覆盖新表。

## 聊天中的直接授权

- `POST /api/threads/{thread_id}/messages` 保留现有身份、会话归属、待预订审批检查和输入防护。父图在允许分支中用确定性规则匹配独立的显式保存指令。成功后回复保存的字段和值。`status` 使用现有可展示状态，保存结果通过 `reply` 返回。
- “请记住：我以后住标准房，优先市区，总预算不超过 400 瑞郎”会在一个事务中保存三个字段。同一指令可表达其中任意字段。仅出现“标准房”“这次住标准房”“我以后想住标准房”时，正常处理原请求。
- 带引号的转述、否定、冲突值、缺少明确币种或总价语义，以及混合了其他动作的保存指令，请用户改成一条明确的保存指令。无法完整解析时无偏好写入，也不会把保存内容转发给模型、FAQ 供应商或 Redis 公共缓存。待预订审批时，聊天输入沿用原有阻塞规则，账号偏好 API 仍然可用。
- 聊天保存与该轮图检查点在现有会话锁事务内提交。原始消息依旧由现有入口保存。如果图事务失败，偏好更新回滚。读取消息、获取检查点或恢复审批都不会重新执行旧保存指令。
- 首版沿用现有聊天页面展示保存结果。读取、修改和删除可通过正式 API 执行，独立网页设置面板留待后续需求。

## 酒店查询与历史恢复

父图构造酒店查询时按字段取值，先用当前请求的明确条件，再用当前未完成酒店请求或这次显式引用的早期请求中的明确条件，最后使用 PostgreSQL 中此刻有效的账号偏好。偏好查询仅在实际准备执行酒店搜索时发生。预算作为库存查询约束下推到按房型与币种分组后的整段住宿总价过滤，先过滤再应用现有返回上限。酒店角色收到经核验的到达信息和生效的查询参数。

- 在父图检查点记录本会话最近一次成功核验并执行的酒店查询意图，包含航班编号、住几晚或明确退房日期、当时由用户明确提供的区域、房型和总预算，以及对应的原始消息引用。记录采用可序列化的结构化字段。返回酒店或确认无库存都更新这条记录。工具故障、超时、航班核验失败和仍在追问时保留上一条记录。自动补入的跨会话偏好和供应商回复不进入记录。
- 再查时读取本人当前会话的记录及相应原文引用。短语“按上次的酒店条件再查”与“按上次的酒店条件再查，这次住市区”覆盖首版恢复入口。有效的再查指令沿用新酒店请求的行为，替换当前未完成酒店查询，使用所引用的历史和这次明确给出的字段。航班与本地到达日期重新核验，酒店价格与库存重新查询。当前条件无法明确解析时先追问。找不到有效记录或原文时，请用户重新给出酒店条件。无法形成新的有效请求时保留当前未完成查询。取消活跃酒店查询时清除对应活跃状态，已执行查询的历史仍可由显式再查指令引用。
- 在多轮追问中保留来源，允许航班编号和住宿晚数来自不同消息。普通对话或独立 FAQ 不覆盖最近一次酒店查询记录。历史恢复限定同一用户的同一会话。早期原文保留在现有业务消息表。旧检查点缺少新字段时按无可恢复记录处理，继续支持原有查询和审批。
- 首版使用结构化事实和带归属的消息回查。通用语义检索、全文拼接和异步摘要以后单独验证。已展示的酒店选项及已保存的预订提案继续按现有库存、价格和审批规则处理。

## 验收

1. 用两名合成账号验证未登录拒绝、读取和更新仅作用于本人、原子字段更新、删除幂等、旧迁移升级及旧数据保留。
2. 验证显式保存一次成功，无需二次确认。对仅表达旅行条件、否定、引号转述、模糊预算、受拒输入及待审批阻塞没有偏好写入。确认失败的图事务无偏好副作用。
3. 同一账号新会话使用已保存房型、区域与总预算。当前请求可覆盖默认值，修改下次生效，删除后从旧会话或旧历史重新查询也不会复活偏好。验证多晚累计价格、总价边界和筛选先于条数限制。
4. 构造带跨午夜航班的多轮对话，经至少六个无关对话回合及应用重启后恢复原始住宿约束。验证提供明确新约束时用新约束，另一次未完成查询的字段不会混入再查，无库存更新历史，角色超时保留上一条历史。跨用户和跨会话读取早期消息失败，缺失旧检查点字段或原文时给出可继续对话的回复。
5. 复跑 P6–P9 相关测试、根和角色套件，并用正式 FastAPI 启动执行本机 HTTP 测试。需要数据库的验收使用真实本地服务，角色走清楚标注的离线模式，无收费模型调用。记录原始输出和临时资源清理结果。
