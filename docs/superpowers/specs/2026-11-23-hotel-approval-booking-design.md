# P7 · 网页审批与演示酒店预订

状态：已审批。接续正式仓库 `main` 的 `2f43dc3`，沿用 P6 会话、酒店查询结果和两套锁定依赖。

## 用户流程

已登录用户从当前会话的酒店推荐中点「发起演示预订」，明确选择一家酒店和一个房型。页面随后展示服务端提案，包括酒店、房型、入住与退房日期、总价、币种和有效期，并提供「确认预订」和「拒绝」。第一步生成提案，第二步才允许进入预订执行。确认成功后展示订单和回执。全部结果标明为演示。P7 操作本机 PostgreSQL 合成数据，真实支付、外部下单和取消已确认订单留在后续范围。

提案拟采用 10 分钟有效期，每个会话同时只允许一个待处理提案。用户可在等待期间刷新或重新打开会话。修改住宿条件时先拒绝旧提案，再重新查询和选择。到期或库存、价格变化后，旧提案关闭，页面提示重新查询和确认。已接受决定的恢复工作仍占用该会话，系统完成恢复后接受下一轮消息。

## 正式接口和数据边界

- `POST /api/threads/{thread_id}/hotel-proposals` 接收 `message_id` 与 `option_index`。服务端从同一用户、同一会话的最新 P6 推荐快照选取该选项，重新读取酒店、整段库存和价格。客户端只能选择结论中的一个索引。原始日期、房型和价格由服务端取得。推荐已过时、价格已变化或已有不同的待处理提案时返回可识别冲突。重复提交同一选择时返回当前提案；终止后形成新提案需有新的推荐轮次。
- `POST /api/threads/{thread_id}/approvals/{action_id}/decision` 仅接收 `decision: approve | reject`，参数严格校验。恢复前验证当前会话归属、提案归属和有效期。跨账号、跨会话及未知 ID 使用一致的 404；相反决定返回 409；同一决定的重试返回已有结果或继续恢复。并发请求争锁失败时可返回 409，客户端按状态确认后重试。
- `GET /api/threads/{thread_id}` 从业务数据库投影该会话当前或最近的审批、回执状态。过期、拒绝、库存或价格变化、完成可区分。若已有决定而检查点仍等候恢复，页面展示「继续处理」，由用户重交原决定。无决定的过期提案可由下一条消息收束。重复读和刷新具有同一效果。查询状态无预订副作用。P6 消息和工具 HTTP 契约维持兼容。

## 父图暂停与恢复

采用现有父图内的命名执行节点，持久化提案及待恢复检查点后暂停。拟使用现有版本支持的静态中断点，在决策持久化后沿同一 `thread_id` 恢复同一节点。交接状态保存服务端 `action_id` 和来源引用，保留现有 JSON 检查点格式和旧会话。对比在 HTTP 层直接预订，父图拥有批准后唯一写入路径；对比把审批决定只放在恢复参数中，业务表保留的决定可以在进程退出后重新核验。精确版本验证在实施计划中锁定。

1. 复用 P3 的线程级 PostgreSQL 事务锁和进程内并发限制，覆盖提案生成、提交决定和普通消息。核验待处理状态发生在写入普通消息前。处于待确认或待恢复状态的会话拒绝新消息。已过期的纯待确认提案可在下次持锁操作时收束，随后开放消息。
2. 提案记录和暂停检查点在持锁的同一 PostgreSQL 事务提交，防止只留下业务提案或只留下暂停状态。生成失败则整轮回滚。状态和快照由服务端产生。
3. 外层连接持有线程事务锁并负责图检查点。在其持锁期间，独立业务事务提交首个不可更改的决定，然后由原持锁连接恢复父图。订单事务再使用独立业务连接提交。持锁连接在恢复路径中不事先锁定提案行，以免阻塞独立事务。执行节点读取已存决定并核验归属，先按 `action_id` 查回执，再检查有效期和当前库存。发现成功回执时直接完成图状态。若业务提交成功但图事务断开，再次恢复也复用该回执。普通请求和角色模型没有能力调用预订写入。
4. 已拒绝、已过期或已确认的提案均能收束父图。过期检查以数据库时钟为准。已成功预订的回执在到期后仍有效；仅已接受批准而未成功预订的提案，执行时若已到期则关闭为过期。若已有不可更改的决定，相反决定返回 409；同一决定返回当前终态或继续恢复。无决定的已过期提案对两种新决定均返回过期。读取状态时可以展示逻辑过期；下一次持锁的消息或审批请求负责清理暂停状态，状态读本身不触发订单写入。

## 业务一致性与审计

增量迁移新增 `hotel_booking_proposals`、`hotel_bookings`、`hotel_booking_receipts`。提案绑定用户、会话、源消息、选项和到期时间，保存每晚的数量、价格和币种快照。数据库约束保证一个会话至多一个待处理提案，并保证订单及成功回执的 `action_id` 唯一。审批变更和订单状态来源以业务表为准，检查点只存引用。既有业务 schema 与历史检查点通过回归验收。

批准节点在一个业务事务中先锁定目标提案，再按稳定顺序锁定整段库存行。对照快照比对每晚的数量、价格和币种，并检查余量为正。任何一晚不一致都整体终止为过时；库存保持原值。匹配时每晚扣减一个房间，同时写入一笔订单、唯一成功回执并关闭提案。事务异常时整体回滚。失败或超时默认无自动写重试。再次请求先查回执，再按已持久化的决定推进。

在统一工具层增加专用于已批准预订的受控调用路径。既有角色的工具注册保持只读。业务成功回执与订单同事务，`tool_audit_logs` 沿用独立限时写；保留 `action_id`、会话和调用标识，记录尝试和结果，过滤凭据、用户私有正文和付款数据。审计不可用时以业务回执为准，并发出已有的脱敏故障日志。

## 验收

- 通过正式 launcher 的网页与 HTTP 路径建立提案，刷新和重启后可继续。确认前不扣库存；成功后所有住宿日期各减一，订单与回执各一条。重复确认返回同一个订单，重复拒绝返回同一个终态。
- 拒绝、已过期、伪造金额、越权访问、无有效决定、库存变更、单晚价格或币种变更均无法创建订单或扣减库存。价格变化测试覆盖总价相同但夜价发生变动。
- 同一会话并发消息与确认持同一把锁；同一提案重复和并发确认只执行一次。不同线程或账号竞争最后一间房时只有符合最新快照的一方成功。事务中途异常不会留下部分库存更新。
- 注入「决定已保存但未执行」和「订单已提交但检查点提交失败」。重启后真实 HTTP 状态提供继续处理入口，原决定重提交使原会话恢复，库存只扣一次。测试同时覆盖批准后跨过有效期、成功回执到期后重放、过期后的消息恢复，以及另一个账号不能看见提案、回执或预订内容。
- 复跑两套环境全量与现有 P6 E2E，新增 P7 真 PostgreSQL、真实 HTTP 验收，测试 schema 隔离并清理。默认付费请求为零。
